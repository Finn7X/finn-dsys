做 Agent 系统最让人头疼的不是 prompt 写得好不好，是 Agent 上线后各种"不听话"。模型有时候不搜索就直接编答案，有时候搜了十几次同一个关键词停不下来，有时候超时了给用户返回一个半成品回复。

我们团队有七八个不同的助手（周报、培训、产品文档、交付等），最初每个助手各写一套 Agent 逻辑，维护成本极高。后来抽象出了一个公共框架，统一处理这些生产环境的"脏活"。今年 OpenAI 发了 Harness Engineering 的论文之后回头看，我们做的本质上就是同一件事——不是优化模型，而是优化模型的控制系统。

## Agent 在生产环境中"不听话"的几种方式

先列几个实际遇到的问题，后面的设计都是为了解决这些：

**不搜索就直接答。** 用户问"R6900 G5 支持多大内存"，Agent 直接说"512GB"——结果是它自己编的。正确答案要从知识库检索。

**无限循环搜索。** Agent 搜"许计峰 工作"没找到满意结果，然后搜"许计峰 工作内容"、"许计峰 工作进展"——本质上是同一个 query，但它停不下来，一直搜到递归上限报错。

**多轮对话丢上下文。** 第一轮讨论运营商网络部署，第二轮用户说"只看联通的"，Agent 不知道"联通"是在筛选上文的什么内容，把它当成一个全新的问题处理。

**超时后回复残缺。** Agent 做了大量检索但来不及整合就超时了，给用户返回"我需要更多信息"或者空字符串。

## 中间件链：用确定性逻辑约束概率性行为

我们的方案是在 LLM 调用前后插入一系列中间件，形成一条执行链。每个中间件负责一个具体的行为约束：

```python
# 中间件按执行顺序排列，顺序很重要
middleware = [
    StaleMessageCleanupMiddleware(),     # 清理上轮残留指令
    ForceFirstSearchMiddleware(),        # 强制首次检索
    MinToolCallsMiddleware(),            # 最小工具调用次数
    MaxToolCallsMiddleware(),            # 最大工具调用（安全网）
    ContextEditingMiddleware(),          # 清理早期工具输出
    SummarizationMiddleware(),           # 上下文摘要压缩
    ModelFallbackMiddleware(),           # 模型降级
]
```

**ForceFirstSearch** 解决"不搜索就直接答"的问题。工作原理是在第一次 LLM 调用前注入一条系统指令要求先搜索，如果 LLM 的回复中没有工具调用，再注入一条更强硬的提醒。最多注入 2 次就放弃——避免无限注入撑爆 context。

**MaxToolCalls** 解决无限循环。设了两个阈值：总工具调用不超过 25 次、搜索不超过 15 次。超过后强制停止工具调用，让 Agent 基于已有结果回答。这个值是根据线上数据统计的：正常查询 3\~8 次，复杂查询 10\~15 次，超过 25 次基本是死循环。

**执行顺序为什么重要？** StaleMessageCleanup 必须排第一。因为多轮对话中，checkpointer 会恢复上一轮的完整 state，其中包含 ForceFirstSearch 上一轮注入的"强制搜索"指令。如果不先清理这些残留指令，新一轮的 ForceFirstSearch 会看到旧指令误判状态。

## 会话管理：冷启动 vs 热继续

多轮对话的核心问题是：Agent 怎么知道用户的新 query 是接着上一轮聊，还是换了个话题？

我们的方案分两级判断：

**第一级，关键词快速路径。** 用户说"重新查"、"不对"、"错了"、"接着说"这些，肯定不是话题切换——直接返回"不切换"，不调 LLM。这一步零延迟。

**第二级，LLM 判断。** 把最近 5 条用户消息和当前 query 传给一个轻量模型，让它判断是否切换了话题。temperature 设为 0 保证确定性。

判断结果决定两种不同的处理路径：

- **冷启动**：新建 session，注入虚拟文件（skills、references）和历史摘要到 system prompt
- **热继续**：从 checkpointer 恢复上一轮的完整 state，对 query 做上下文感知改写

上下文改写是热继续的关键。用户说"只分析联通"，原始 query 缺少上下文。我们检测到这是过滤筛选类表达后，自动改写为"帮我分析三大运营商的5G核心网部署情况，只分析联通"——把上一轮的话题拼进去，让检索工具能理解搜什么。

## 异常恢复：从半成品中抢救答案

Agent 超时或递归超限时，不能直接返回错误。用户等了几十秒，至少应该拿到一个基于已有检索结果的回答。

恢复策略分两层：

**策略一（优先）：从工具结果整合。** 从 checkpointer 的 partial state 中提取所有成功的 ToolMessage，用一个独立的 LLM 调用基于这些工具结果重新生成回答。通常 Agent 超时是因为在整合阶段卡住了，但之前的检索结果都是好的——用这些结果重新生成比什么都没有强得多。

**策略二（回退）：提取最后的 AI 回复。** 如果 Agent 在超时前已经开始输出回复（>=100 字），直接截取。虽然不完整，但比空好。

实际跑下来，策略一成功率在 70% 以上——大部分超时场景都是 Agent 做了 5\~6 次检索后在整合时超限，工具结果本身是有价值的。

## 后处理：答案质量兜底

Agent 有时候会返回技术上"成功"但内容上残缺的答案——比如只说"已为您整理以下信息"但后面没有实际内容，或者回复中混入了中间件注入的系统指令文本。

我们有一个 `AnswerConsolidator` 做最后一道检查：

```python
# 检测模式
INCOMPLETE_PATTERNS = ["已为您整理", "已为您梳理", "如需了解"]
MIDDLEWARE_LEAKAGE = ["【强制检索要求】", "【系统指令】"]
RAW_TOOL_MARKERS = ["<|tool_calls_section_begin|>"]

# 判断逻辑
if tool_calls_count >= 4 and len(answer) < 150:
    # 搜了 4 次但回答不到 150 字，大概率内容丢了
    → 触发整合：从 ToolMessage 中重新生成完整答案
```

这个检查器是保守策略——只在明显异常时触发，避免对正常回答做不必要的二次处理。

## 可观测性

上面说的所有环节，如果看不到内部状态就没法调优。我们用 Langfuse 做全链路追踪，在 `generate_reply()` 的关键节点创建 Span：

```
generate_reply()
  → session_resolve (冷/热判断、话题检测结果)
  → memory_retrieval (记忆召回耗时和命中情况)
  → query_rewrite (改写前后对比)
  → agent_build (工具列表、skill 文件数)
  → [LangGraph invoke] (框架自动追踪每次 LLM 调用和工具调用)
  → tool_call_stats (工具调用次数、名称)
  → answer_consolidation (是否触发补救)
```

所有 Langfuse 操作都包在 try/except 里，失败时静默降级为空操作——可观测性不能影响主链路。

## 回过头看

这套框架跑了几个月，几个观察：

**中间件是最有价值的设计。** 它把"Agent 应该怎么做"从概率性的 prompt 指令变成了确定性的代码约束。ForceFirstSearch 不是在 prompt 里写"你必须先搜索"（Agent 可能忽略），而是检测到没搜索就注入系统消息强制要求，检测到还没搜就再来一次。这比单纯调 prompt 可靠得多。

**话题检测的误判率比预期高。** 特别是用户说"汇总成表格"这种格式变换请求，LLM 经常误判为话题切换。关键词快速路径拦截了一部分常见追问，但不是所有 case 都能用关键词覆盖。这个问题目前还没有特别好的解。

**MinToolCalls 有副作用。** 对"你好"这种闲聊，强制搜索 2 次完全是浪费。应该根据 query 类型动态跳过——但判断 query 类型本身又需要一次 LLM 调用。最后权衡下来觉得：浪费两次搜索的延迟可以接受，误漏搜索导致编造答案不可接受，所以保留了强制策略。
