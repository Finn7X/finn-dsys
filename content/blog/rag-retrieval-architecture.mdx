去年下半年我在做一个企业内部的知识库问答系统。知识库里有产品手册、周报月报、培训课程等各类文档，chunk 数量大概几十万量级。最开始用的是单路向量检索，效果还行，但随着文档量增长，有些场景开始暴露问题——比如用户搜产品型号 "R6900 G5" 的时候，纯语义检索经常把其他型号的文档也召回来；反过来，用户问"设备为什么老重启"这种口语化表达时，关键词检索又完全不知道该匹配什么。

这篇记录一下最后演化出来的三路并行检索架构，以及过程中的一些工程决策和反思。

## 为什么最终选了三路并行

单路检索的核心矛盾在于：向量检索擅长理解语义但对精确术语无力，BM25 擅长关键词匹配但不理解自然语言。没有一种策略能同时覆盖所有场景。

我们最终跑的三路策略：

**Hybrid**（KNN + BM25 混合）—— 向量和关键词同时参与，ES 8.x 原生支持 `knn` + `query` 并行执行，最终分数叠加。这是主力策略，大部分 query 靠它就够了。

**Semantic**（纯 KNN）—— 把向量搜索的召回窗口开到 k=80（Hybrid 只用 k=50），作为语义兜底。为什么 Hybrid 里已经有 KNN 了还要单独跑一路？因为 Hybrid 的最终排序会被 BM25 分数干扰——一个文档如果语义高度相关但没有关键词命中，它在 Hybrid 中的排名会被 BM25 高分的文档压下去。纯 Semantic 路能把这些被"误伤"的文档捞回来。

**Phrase**（短语精确匹配）—— 专门处理产品型号、技术术语等精确匹配需求。权重设为 0.6（低于前两路的 1.0），防止纯字面匹配的文档排名过高。

三路用 `ThreadPoolExecutor` 并行执行，各自有独立的超时（Hybrid 1500ms、Semantic 1200ms、Phrase 800ms）和降级策略。任何一路失败不影响其他两路。

## 多路融合：归一化 + 加权 + 去重

三路返回的分数量纲完全不同——BM25 分数范围 5\~50+，KNN cosine 分数 0\~1，直接比较没有意义。融合流程分三步：

**第一步，Min-Max 归一化。** 对每一路独立做 `(score - min) / (max - min)`，把分数映射到 [0, 1]。这里有个边界 case：如果某路只返回一个结果，`max == min`，归一化会除零，代码里直接跳过了。

**第二步，乘以策略权重。** `hybrid × 1.0, semantic × 1.0, phrase × 0.6`。Phrase 乘 0.6 意味着即使它给某文档打了归一化满分 1.0，加权后也只有 0.6，不会压过 Hybrid/Semantic 的高分文档。

**第三步，按文档 ID 合并去重。** 同一个文档可能被多路同时命中。去重策略是取该文档在所有策略中的最高加权分，同时记录命中来源。

举个实际的数值例子。假设 Hybrid 给 doc\_A 打了 12.5 分（归一化后 1.0 × 1.0 = 1.0），Semantic 也给它打了 0.87（归一化后 1.0 × 1.0 = 1.0），最终 doc\_A 的分数还是 1.0——因为取的是 max 而非累加。这其实是当前设计的一个缺陷：**多路命中这个信号被浪费了**。如果改成累加 + 命中次数加分，doc\_A 可以拿到更高的分数，更好地和单路命中的文档拉开差距。

## Rerank 的服务端优化

粗排之后我们用 Qwen3-Reranker-8B 做精排。Cross-Encoder 的准确率比 Bi-Encoder 高不少，但部署的时候遇到一个问题：默认的 prompt 模板下，Reranker 输出的分数区分度很差——相关文档和不相关文档的分数都集中在 0.3\~0.7 之间，用 `min_score=0.5` 过滤时要么漏掉好结果、要么放进来一堆垃圾。

解决方案是在 vLLM 和业务代码之间加了一层 FastAPI 代理，用自定义 Jinja2 模板改写了输入 prompt。关键改动是在模板里加了 `<think>\n\n</think>` 空思考标记——引导模型跳过推理过程直接输出判断，配合 `classifier_from_token: ["no", "yes"]` 让 vLLM 直接输出 "yes" token 的 softmax 概率作为分数。

优化后分数分布变得极端化：相关文档集中在 0.70\~0.98，不相关文档集中在 0.02\~0.30，`min_score=0.5` 的分界效果好了很多。

## 超时降级

三路策略的超时降级策略不同，因为瓶颈不同：

Hybrid 超时通常是 BM25 的 Bool Query 太复杂，降级策略是砍掉 BM25 只保留 KNN——去掉复杂度瓶颈，快速返回纯语义结果。Semantic 超时是 KNN 遍历候选太多，降级策略是把 `num_candidates` 从 500 缩小到 150——缩小搜索范围，牺牲一些召回换速度。

降级后结果质量会下降，但总比超时返回空好。这里有个后续可以改进的点：降级发生时应该在结果中标记 `degraded: true`，方便线上监控降级频率。

## 数据处理层面的优化

检索质量不光取决于检索策略，数据处理也很关键。我们做了两个专项优化：

一是**表格结构化保留**。网页文档里经常有表格，如果直接提取为纯文本，行列关系会完全丢失。我们写了一个 HTML 解析器，用状态机追踪表格上下文（支持嵌套表格，用栈管理），在提取时保留 `<table>/<tr>/<td>` 标记。超长表格每 20 行自动分页并重复表头，这样即使 chunk 切分在表格中间，每个片段都有完整的表头信息。

二是**PPT 的视觉模型分析**。PPT 和文本文档不同，它是视觉化的——图表、排版、色彩标注都承载信息。我们用视觉模型（VLM）对每页 PPT 截图做两步分析：先分类（标题页/目录页/内容页/感谢页），再提取内容。目录页会额外识别当前高亮的章节，用来给内容页建立章节归属关系。最终入库时，非内容页被过滤掉，内容页的路径前缀包含了章节信息（如 `"项目总结.pptx / 二、技术方案"`），检索时 LLM 可以准确回答"这个方案在文档的哪个部分"。

## 回过头看

这套架构跑了几个月，整体效果还行，但有几个地方如果重做会换个方式：

Min-Max 归一化对极端值太敏感。某路有一个异常高分文档时，其余文档的归一化分数都被压缩到很低。Z-score 或分位数归一化会更稳健。

策略权重硬编码不够灵活。关键词型 query（"R6900 G5 内存规格"）理应让 Phrase 权重更高，自然语言 query（"这个产品内存兼容性怎么样"）理应让 Semantic 权重更高。后来在另一个模块里做了 Query Classification 来动态调权，但检索服务本身还没接入。

自适应质量过滤有个 bug：`query.split()` 判断"短查询"，对中文完全无效——中文没有空格分词，所有中文 query 都被当成"短查询"处理。这个问题发现得比较晚，暴露了纯单测不够、需要中文 query 评测集的问题。
