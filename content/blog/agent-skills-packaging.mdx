我们有七八个不同的助手，底层都在做同一件事：从知识库检索文档、获取详情、整理回答。但每个助手的 prompt.py 里各写了一遍检索流程——120 行的 Python f-string，内联了索引路由规则、工具使用策略、检索深度要求等等。改一个检索策略要改七八个文件，经常漏改。

今年 Anthropic 开放了 Agent Skills 标准之后，我试着把"知识检索问答"这个能力从各助手中提取出来，封装成一个独立的 Skill。过程中对 Skill 的设计哲学有了一些体会，记录一下。

## Skill 的本质：一个目录

Agent Skills 的格式其实很简单——一个目录，里面有一个 `SKILL.md` 文件。就这样。

```
knowledge-retrieval/
├── SKILL.md              ← YAML 元数据 + Markdown 指令
├── references/           ← Agent 按需读取的参考文档
│   ├── index-catalog.md
│   ├── retrieval-strategy.md
│   └── output-format.md
└── assets/               ← 框架消费的结构化配置
    └── index-routing.yaml
```

SKILL.md 分两部分：YAML frontmatter 声明"我是谁、什么时候该用我、需要什么工具"，Markdown 正文写"具体怎么做"。

```yaml
---
name: knowledge-retrieval
description: >
  Enterprise knowledge base retrieval and Q&A skill.
  Use when user asks about project progress, weekly reports,
  product documentation, training materials...
allowed-tools: knowledge_search fetch_page_content
---
```

这个 description 是关键——Agent 启动时只加载每个 Skill 的 name 和 description（大概 100 tokens），用来判断当前 query 该不该激活这个 Skill。只有决定激活之后才读 SKILL.md 正文，正文中引用的 references/ 文件则是 Agent 觉得需要时才读。这就是所谓的"渐进式加载"（Progressive Disclosure）。

## 渐进式加载到底省了多少

算一笔账。我们的检索能力涉及四块内容：核心流程（800 tokens）、索引说明（600）、检索策略（800）、输出格式（600），加起来 2800 tokens。

如果全量注入 system prompt（之前的做法）——不管用户问什么，每次 LLM 调用都带着 2800 tokens 的检索指令。

用渐进式加载之后：

简单事实查询（"R6900 支持多大内存"）——激活 Skill 读正文 800 tokens，写回答时读 output-format 600 tokens，不需要读索引说明和检索策略。总共 1400 tokens，**省了 50%**。

复杂多角度查询（"对比三大运营商的 5G 部署"）——需要选索引、需要深度检索策略，全部 reference 都会被读取。总共 2800 tokens，和全量注入一样。但这种复杂查询的频率大概只占 20%。

按查询类型分布加权算，平均 token 消耗降低约 40%。这不只是省钱——更重要的是减少了注意力稀释，LLM 对真正需要关注的指令执行得更好。

## 从 prompt.py 里提取了什么、保留了什么

这是整个 Skill 化过程中最需要想清楚的问题。原则是：**Skill 定义不变的能力，prompt 定义变化的上下文。**

提取到 Skill 中的（跨助手不变）：
- 检索流程的 5 步骤（分析问题 → 选索引 → 执行检索 → 构建回答 → 个人问题处理）
- 工具使用规范（怎么用 knowledge\_search、什么时候用 fetch\_page\_content）
- 输出格式要求（纯文本、引用规范、禁止行为）
- 索引路由规则（关键词 → 索引映射）

保留在各助手 prompt 中的（每次调用可能不同）：
- 当前时间 `current_time`
- 用户信息 `user_info`（姓名、部门、职位）
- 群聊上下文（SSP 群自动加 SSP 索引）
- 历史对话摘要

索引路由规则放在 `assets/index-routing.yaml` 里，而不是写在 SKILL.md 正文中——因为它是给框架代码解析的结构化数据，不是给 LLM 读的自然语言。不过 SKILL.md 正文的 Step 2 中仍然有一份人类可读的路由说明，算是双保险：框架自动路由 + Agent 也知道路由逻辑可以手动覆盖。

## references/ 为什么拆成三个文件

拆分的依据不是内容分类，而是 **Agent 需要的时机**：

- `index-catalog.md`——Step 2 选索引时才需要，简单查询（默认索引就够）完全不用读
- `retrieval-strategy.md`——Step 3 首次搜索不理想时才需要，搜一次就命中的情况不用读
- `output-format.md`——Step 4 写回答时才需要，每次都会读

如果把三者合并成一个大文件，Agent 每次都要读全部，哪怕当前 query 只需要其中一部分。拆开之后 Agent 按需读取，减少了上下文噪声。

## Skill 和 MCP 是什么关系

经常有人问 Skill 和 MCP（Model Context Protocol）有什么区别。简单说：

**MCP 定义 Agent 怎么连接工具**——类似 USB 接口标准，规定了 API 格式、认证方式、数据结构。我们的 `knowledge_search` 工具背后连接 Elasticsearch 的配置、`fetch_page_content` 连接 iCenter API 的逻辑，这些属于 MCP 层面。

**Skill 定义 Agent 连上工具后怎么用**——搜几次、怎么判断结果够不够、怎么组织回答。同样的 `knowledge_search` 工具，检索产品文档和检索周报的策略完全不同（前者侧重精确型号匹配，后者侧重多角度人员/项目/时间交叉搜索）。

所以它们是互补的：MCP 负责"接上"，Skill 负责"用好"。只有 MCP 没有 Skill，Agent 有工具但不知道怎么高效使用；只有 Skill 没有 MCP，Agent 有流程但连不上工具。

## 跨助手复用的效果

封装完成后，各助手的接入方式变了：

```python
# 之前：每个助手手动拼十几个参数
service = DeepAgentService(
    service_name="weekly",
    system_prompt_generator=gen_agentic_system_prompt,  # 120 行 Python 函数
    index_names=["weekly_all"],
    soul_path="weekly/soul.md",
    output_rules_path="weekly/output_rules.md",
    enable_searcher_subagent=True,
    # ... 更多参数
)

# 之后（目标）：Skill 声明检索能力，soul 声明角色
service = DeepAgentService(
    service_name="weekly",
    soul_path="weekly/soul.md",           # 每个助手不同
    skills=["knowledge-retrieval"],        # 共享的检索能力
)
```

新增一个助手不再需要复制粘贴 prompt.py，只要写一个 soul.md 声明角色定位就行。检索流程、索引路由、输出规范全部从 Skill 继承。

SSP 助手有额外的型号过滤逻辑（wildcard filter + 双知识库合并），这部分不适合放进通用 Skill，可以封装为独立的 `ssp-product-filter` Skill，和 `knowledge-retrieval` 组合使用。

## 回过头看

Skill 本质上是把 Harness Engineering 中的"能力层"标准化了。之前的中间件约束了 Agent 的行为边界，记忆系统提供了持久化知识，而 Skill 定义了 Agent 的可复用能力——三者组合在一起就是一个完整的 Harness。

一个比较有意思的观察：Skill 的渐进式加载设计和人类认知其实很像。你不会在接到任何任务时都把所有知识装进脑子里——你先想"这个任务需要什么技能"，然后只调取相关的经验和知识。Agent 也应该如此。全量注入等于让 Agent 每次都"复习全部教材"，渐进式加载等于让它"按需翻阅参考手册"。

目前 Skill 还只在我们内部框架中使用。因为 Agent Skills 是开放标准（Anthropic 发起，Microsoft、OpenAI、Cursor 等已经采纳），理论上同一个 Skill 可以直接迁移到其他支持该标准的平台上——不过跨平台移植时工具名称映射还是需要适配层的。
